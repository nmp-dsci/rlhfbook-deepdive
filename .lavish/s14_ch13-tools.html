Chapter 13: Tool Use and Function Calling

Model weights alone cannot know today's news or move a file. Tools fix both, and tool use is a skill that RLHF and every other method in the book can train. 1 2 3 Lambert nearly skipped the chapter as "pretty light", then kept it as "really great introductory material", 4 and calls tool use "probably the most lasting skill". 5 The lecture goes well past the book, into 2026 agentic RL. 6

The chapter in five points

  1. Three terms, nested. Tool use is general; function calling adds a declared schema; code execution is the case where the tool is an interpreter. 7
  2. It is all one token stream. The model emits a call, an orchestrator runs it and appends the result, and the model continues. 8 9
  3. Mask the tool output. The model trains on its own calls, not on what the tool returned. 10 11
  4. MCP standardizes the tool side. Servers, clients and hosts, over JSON-RPC 2.0. 12 13
  5. SFT, then preferences, then RL. Multi-step agents learn from environment feedback over a whole trajectory. 14 15

After this chapter you should be able to

  • Tell tool use, function calling and code execution apart.
  • Trace an orchestration loop and say which tokens are trained.
  • Explain MCP's servers, clients and hosts, and what a harness adds.
  • Compare pass@k and pass^k.
  • Say why agentic RL needs environments, and what makes it unstable.

Why models need tools

In Lecture 11: 00:31 · 01:34 · 02:06 · 03:37 · 05:10

"Who is the president today?" fails on the knowledge cutoff but is one search away. 2 Lambert's research models, shown as raw weights, "get things like this wrong because they don't know the future". 16 "Move all the arXiv papers in my downloads folder…" the weights "cannot even attempt". 3 Weights only produce tokens; something must "translate tokens into the real world". 17

So an LLM is now a system: "model weights, tools and harnesses". 18 19 Tools began as "call a calculator"; now search and code execution are the most general primitives on a computer. 20 21 Deep research and computer use came first, culminating in Claude Code and Codex. 22

Three terms, from general to specific

TermWhat it adds
Tool useThe model emits a tool name and arguments; an orchestrator runs it; the result is appended; generation continues. 7
Function callingThe arguments must fit a declared schema, usually JSON Schema, so they can be parsed and validated. 7
Code executionThe tool is an interpreter, "the most general tool of all". 7 23

Code execution lets a model escape its "probabilistic, generative nature". The chapter's example prints pi to 50 digits with the Chudnovsky algorithm instead of reciting it. 24 25 Lambert calls this "a deterministic form of thinking in code", 26 and the slides say tools "remove some of the stochastic elements of 'stochastic parrots'". 27 He also asks which open model recites the most digits of pi correctly without a tool. 28

RAG was one of the first popular tools, now "getting superseded by general search". 34 ReAct's point, quoted in the chapter: "reasoning traces help the model induce, track, and update action plans … while actions allow it to interface with" outside sources. 35 Before it, reasoning and acting were "separate literatures"; o3 is the same idea "scaled up with RL". 36 Lambert says tool use "became very real" in 2025 and calls o3 "one of my favorite models that I've ever tried". 37

Toolformer taught itself tools with synthetic data. The model inserts candidate API calls into its own text, runs them, keeps the calls that "reduce perplexity" on what follows, and fine-tunes on the result. 38 Lambert likens it to the self-instruct line of work. 39

How tool use is evaluated

Exact match on tool name and arguments, schema validity, and end-to-end task completion. 40 The slides order these as "format → selection → consistency → full tasks", 41 and Lambert describes a shift from "can language models follow the format" to "can language models use tools to do complex task". 42 Terminal-Bench 2.0 is now "the most popular evaluation". 43 For consistency, τ-bench introduced pass^k: succeed on all $k$ trials, unlike pass@k's any. 40 41

Same agent, two reliability metrics (my illustration)

pass@k: at least one of $k$ succeeds pass^k: all $k$ succeed

pass@k $= 1-(1-p)^k$
pass^k $= p^k$

At $p = 0.7$ and $k = 8$, pass@8 is almost certain while pass^8 is under 6%. An agent that "usually works" can be unreliable by the second measure. The formulas assume independent trials; see agent notes.

Interweaving tool calls in generation

In Lecture 11: 15:29 · 16:00 · 16:32 · 17:03 · 17:34 · 18:04

Function-calling data is ordinary post-training data plus a system prompt listing the tools, as JSON schemas. 44 Given the chapter's movie tools, a model would emit search_movies("Star Wars"), usually inside special formatting tokens, and the tool's output becomes the next tokens. 45 "The model never 'connects' to anything." 46 47

An orchestrator sits between model and tools. The chapter's loop: call the model; if it made no tool calls, return its text; otherwise run each call and append the result as a tool message. 9 Lambert: "the most basic harness … is a while loop". 48 Executing tools adds a delay, which "makes for a very complex inference situation". 49

    Tool use now appears in office copilots, science, medicine and coding agents such as Claude Code and Cursor. 54 Open models face a harder version: they "must be trained to work with a variety of tools that users may connect off the shelf". 52 Lambert contrasts ChatGPT and Claude Code, "designed for vertical experience". 55

    Model Context Protocol

    In Lecture 11: 18:04 · 18:35 · 19:06 · 19:36

    MCP is an open standard for connecting models to data and systems, using JSON-RPC 2.0 underneath. 12 The chapter calls it "a simple addition" to tool use: a predictable JSON schema for passing data and actions to models. 58

    LayerRole
    ServerWraps one data source or capability; offers resources (read-only data), prompts (templates) and tools (callable functions) 13 58
    ClientAggregates one or more servers, e.g. Claude Desktop or an IDE plug-in 13
    HostThe app the user talks to, e.g. Claude or ChatGPT 13

    The payoff: tool builders write one interface for many models. 59 Lambert is cooler on it; see disagreements. The chapter gives a minimal Python server with one get_weather tool. 12

    Training for tool use

    In Lecture 11: 24:51 · 25:23 · 26:24 · 26:56 · 27:27 · 27:58

    Human tool traces are expensive, so most data is synthetic: Toolformer-style self-labeling or large-scale generation like ToolBench. 79 SFT on trajectories teaches format and tool choice and "is often enough for establishing the foundation"; DPO can improve when to call a tool; multi-step agents learn best from RL with environment feedback. 14 The slides: preference tuning "still works, but is less popular today"; RL is "where the action is". 80 81 For SFT data, the slides point to OpenThoughts-Agent, about 100K trajectories, 82 which Lambert finds "really lightweight on RL details". 83

    Environments are the bottleneck

    Math RL needed prompts and checkers; agentic RL needs environments: containers, file systems, services and tests. 84 "What we have now is prompt with environments with test cases." 85 Making them is hard: it is easy to make trivial tasks and easy to make impossible ones. 86 Much of the generated data gets thrown out. 87 Then the infrastructure: Docker bandwidth limits idle the GPUs, API keys expire, "all these little knife cuts". 88

    A worked case: TMax

    Lambert was on the TMax paper, "one of the last papers for my time at AI2". 89 90 It released about 15,000 terminal environments and trained small open models with outcome-only rewards; TMax-9B reached 27.2% on Terminal-Bench 2.0. 91 He says the data could "sell … for millions of dollars to labs". 92

    Frontier practice, from the lecture

    • Sandboxes over algorithms. Kimi K3 gives its RL algorithm one sentence and environments about seven pages: 51,219,741 sandboxes, idle up to 98% of the time. 101 102
    • Depth is learned. More RL compute raised both scores and the number of steps the model takes. 103 104
    • Harness randomization. Kimi K3 and Nemotron 3 Ultra train across several harnesses, since one fixed harness "can cause a model to overfit". 105 In NVIDIA's Polar, RL through an unfamiliar harness gained 22.6 points, a familiar one 0.6. 106 107
    • The mixing wall. With many domains, each gets few samples per batch, so labs train domain experts and merge them with multi-teacher on-policy distillation. 108 109 On Terminal-Bench 2.0 in Nemotron 3 Ultra, the merged student (54.0) beat its teacher (50.0). 110 See the Chapter 12 page. Q&A 3 adds that industry post-training has "a shocking number of stages", forking and merging. 111
    • Reward hacking. GLM-5's slide policy used overflow: hidden to make slides measure 16:9; Nemotron deletes future git commits; Kimi K3 ships an exploit detector. 112 113 Lambert calls GLM's example "really benign". 114

    More headaches

    Long-tail rollouts (2 tool calls or 200), credit assignment over $10^5$ to $10^6$ tokens, and verifier gaming; TMax rollouts replaced test files with no-ops. 115 With models "working for eight hours at a time", 116 group sampling gets expensive, one reason he thinks GLM-5 used PPO. 117 Agents "manipulate the world so that it passes the test". 118 "So over optimization is back." 119 In Q&A 3 he describes RL as how a model adapts "to the harnesses it'll be used in at deployment". 120 The model and its harness are co-designed, "always a moving target". 121

    Check yourself

    What does function calling add to tool use, and what does code execution specialize?

    A declared schema the arguments must fit; code execution is tool use where the tool is an interpreter. 7

    In the Fibonacci example, which segments does the model train on?

    Its reasoning, its <code> call and its answer. The <output> block is masked, since the tool produced it. 11 10

    When does the orchestration loop stop?

    When the model's response contains no tool calls; the loop returns its text. 9

    An agent succeeds on 90% of single trials. Roughly what are pass@4 and pass^4?

    About 1.00 and 0.66, if trials are independent. pass^k asks for success on all $k$ trials. 41

    Name MCP's three server primitives.

    Resources (read-only data), prompts (templates) and tools (callable functions). 58

    Why is multi-step tool RL "closer to classic RL" than RLHF?

    The agent acts over a whole trajectory in an environment before one reward arrives at the end. 15 56

    Why do Kimi K3 and Nemotron 3 Ultra train under several harnesses?

    One fixed harness "can cause a model to overfit"; scores are model × harness. 105 61

    Agent notes

    agent note The pass^k widget. Not Lambert. It treats trials as independent with one success rate $p$, so pass@k $= 1-(1-p)^k$ and pass^k $= p^k$. Real tasks vary in difficulty, and trials on one task are correlated, so real curves fall less steeply. The definitions are from the slides. 41

    agent note The loop widget. Not Lambert. It counts characters, not tokens, and treats the user prompt as untrained, as usual in SFT. The segment text is copied from the chapter. 51 The chapter's figure says only that tool outputs are masked and tool calls are targets. 11
